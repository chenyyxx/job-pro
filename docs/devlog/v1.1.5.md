# v1.1.5 开发日志

> 发布日期：2026-05-24

## 修复内容

### lilith detail URL — feishu 标准路径

**文件：** `cli/src/lilith.ts:50`

**根因：** `DETAIL_PAGE` 用的是 `${HOST}/career/${id}/detail`，飞书招聘 SPA 这条路由不存在，会 fallthrough 到默认的 SPA shell — 真实 ID 和瞎编 ID 返回的 HTML 完全一样，标题都是「加入莉莉丝」，没有 SSR。和 v1.1.4 修的小红书 `?id=` → `/:id` 是同一类 bug。

**修复：** 改成飞书标准路径 `${HOST}/index/position/${id}/detail`（同样的 feishu 域下 `nio.jobs.feishu.cn` / `xiaomi.jobs.f.mioffice.cn` / `01ai.jobs.feishu.cn` 等都是这个路径）。验证：

```
curl -sL "https://lilithgames.jobs.feishu.cn/index/position/7642636254757112105/detail" | grep -oE "海外创意素材制片"
→ 海外创意素材制片   # SSR 真实标题

curl -sL "https://lilithgames.jobs.feishu.cn/index/position/99999999999/detail" | grep -oE "海外创意素材制片"
→ (空)              # bogus ID 不渲染标题，server-side 区分清晰
```

`CAREER_PAGE` 同步改成 `${HOST}/index/`（搜索 list 页两条路径都可用，统一到新的）。

## URL 体检遗留问题

本次审计跑了 10 个并行 agent 覆盖全部 50 个适配器，curl + bogus-ID 对比法。除了 lilith 已修，还发现这些有 HTTP 层证据的真 bug，后续版本继续修：

- **meituan** — `/job-list/<id>` 在服务器端 302 重定向到 `/web/social` 列表页
- **iflytek + vivo** — 共用 `zhiye.com` SaaS，`?jobAdId=<id>` 服务器不区分，body 完全字节相同
- **unitree** — `/position/<JobCode>` 直接 HTTP 404；上游路由要的是 snowflake 数字 ID（J10126 ↔ 1569894802328125440），parser 需要从 list HTML 的 `<a href>` 抓
- **netease** — `/job-detail?id=<id>` 真实 / bogus / 根目录三个 URL 全是同一个 6083B SPA shell，强嫌疑同小红书 bug
- **antgroup** — URL 形如 `campus-list?positionId=<id>`，结构上是列表页 + filter，不是真正的 detail

还有 8 个 (pingan, trip, liauto, bilibili, weibo, tencent, alibaba) 是 SPA-only 站点，curl 测不出来真伪，需要 headless 浏览器复核才能下结论。

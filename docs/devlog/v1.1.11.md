# v1.1.11 开发日志

> 发布日期：2026-05-24

## 这一轮采用了 agent-browser，curl 体检解决不了 SPA-only 站点

之前用 curl 跑的 URL 体检对 SSR 站点很有效，但有 7 个 SPA-only 站点（pingan、trip、liauto、bilibili、weibo、tencent、alibaba）无法用 HTTP body diff 区分 PASS / FAIL：

- 都是 SPA shell（同一个静态 HTML），content 在 JS 跑完后才填进 DOM
- bogus ID 也返回同样的 shell，HTTP 看不出差别

这一轮换工具：`agent-browser`（vercel-labs，原生 Rust CLI，单条命令驱动 headless Chrome）。每个 adapter 跑：

1. `agent-browser open <real_url> --load networkidle`
2. wait 5s（让 SPA 完成 hydrate）
3. `agent-browser eval 'document.body.innerText.slice(0, 600)'`
4. 同样跑 bogus URL
5. 看 innerText 包不包含真实 title — 包含且 bogus 不包含 → PASS

**复测结果：**

| 适配器 | 浏览器复测 | 备注 |
|---|---|---|
| pingan | ✅ PASS | real 渲染「AI工程化岗 + 完整描述」，bogus 只有导航栏 |
| tencent | ✅ PASS | real 渲染「软件开发-后台开发方向」，bogus 显示「岗位已下架」 |
| alibaba | ✅ PASS | real 渲染「AI数据工程师」，bogus 渲染「- -」空白模板 |
| bilibili | ✅ PASS | real 渲染「推荐算法实习生」，bogus 显示「页面不见了」 |
| trip | 🔴 FAIL | URL pattern 错（详见下文） |
| weibo | 🔴 FAIL | URL pattern 错（详见下文） |
| liauto | ⚠️ 上游数据问题 | URL 路由 SPA 认识，但所有 ID 都被后端 reject |

## 修复内容

### trip detail URL — 用 MJ-code + hash 路由

**文件：** `cli/src/trip.ts:99-107`, `161-179`, `197-209`

**根因：** 旧 `DETAIL_PAGE` 是 `https://careers.ctrip.com/campus/job-detail/${jobId}` 其中 `jobId` 是 raw API 里的 UUID（如 `e8ffc4de-0cc2-4687-b1d9-690aa2c8afa3`）。这个 URL 在浏览器里渲染的是携程招聘首页公司介绍轮播 — `/campus/job-detail/<UUID>` 不是 SPA 注册的路由。

**研究方法：**

```bash
agent-browser open "https://careers.ctrip.com/campus#/jobList"
agent-browser eval 'document.querySelectorAll("a[href*=\"job-detail\"]")'
# → 全是 https://careers.ctrip.com/campus#/experienced/job-detail/MJ034732 形式
```

SPA 用 hash 路由 + MJ-代号。`MJ034732` 这个值在 raw API 里是 **`fromId`** 字段（之前 adapter 没解析）。直接 curl API 确认：

```json
{
  "id": "27890040",
  "fromId": "MJ029167",
  "jobId": "02014009-a740-4ba5-b2b7-fbeef4c37524",
  "jobTitle": "英语客服（用车）(MJ029167)",
  ...
}
```

**修复：**

1. `RawJobAd` 加 `fromId?: string` 字段
2. `DETAIL_PAGE(mjCode)` 改成 `https://careers.ctrip.com/campus#/experienced/job-detail/${mjCode}`
3. `summarizePosition` 用 `item.fromId` 不再用 `item.jobId`

实测：

```bash
$ agent-browser open "https://careers.ctrip.com/campus#/experienced/job-detail/MJ029167"
"英语客服（用车）(MJ029167) ... 职位描述 ... 处理客户的产品咨询、预订等问题..."

$ agent-browser open "https://careers.ctrip.com/campus#/experienced/job-detail/MJ00000000"
"... 您查看的职位已下架，可查看其他招聘中的职位并投递 ..."
```

### weibo detail URL — Moka hash 路由用单数 `#/job/<id>`

**文件：** `cli/src/weibo.ts:212-217`, `353-356`

**根因：** 之前 `apply_url` 是 `https://app.mokahr.com/social-recruitment/sina/${siteId}/job/${id}`（path segment 形式）。Moka SaaS 用的是 hash 路由 — 这条 URL 在 server 层就被认成"页面不存在"返回 title="您访问的页面不存在"。

**研究方法：** 让浏览器跳到 sina 招聘的 jobs list 页，dump 页面里所有 `<a href>`：

```bash
agent-browser open "https://app.mokahr.com/social-recruitment/sina/43535#/jobs"
agent-browser eval '[...document.querySelectorAll("a[href]")].map(a => a.href)'
# → https://app.mokahr.com/social-recruitment/sina/43535#/job/20fd2233-...
# → https://app.mokahr.com/social-recruitment/sina/43535#/job/43065918-...
```

注意：sina 用的是**单数 `#/job/<id>`**（其他 Moka 租户如 moonshot / megvii 是复数 `#/jobs/<id>`），看起来每个租户自己注册路由。

**修复：** 改成 `https://app.mokahr.com/${channel}-recruitment/sina/${siteId}#/job/${id}` — 加 `#` 分隔。`fetchPositionDetail` 路径也同步修改。

实测真实 ID 渲染了「用户增长产品经理 + 完整描述」，bogus UUID 显示 list-page 空模板。

## 已知问题

### liauto 详情页对所有 ID 报"请前往职位列表重新查找"

**现象：**

```bash
# 来自 CLI search 的 fresh ID
$ npx tsx src/index.ts liauto search | jq -r '.positions[0]'
{ "post_id": "18450", "title": "高速选址运营实习生", ... }

# 直接打开
$ agent-browser open "https://www.lixiang.com/job/detail/18450.html"
"请前往职位列表重新查找该职位"

# 试 code 字段
$ agent-browser open "https://www.lixiang.com/job/detail/A250382.html"
"请前往职位列表重新查找该职位"

# 试社招 + ?fromJob=1 query
$ agent-browser open "https://www.lixiang.com/job/detail/512.html?fromJob=1"
"请前往职位列表重新查找该职位"
```

公网详情页对任何 ID 都识别成「职位详情」route 但找不到对应 ID。直接 curl `api-web.lixiang.com/.../job/list` 返回 `100012 没有接口访问权限`，但 `/school/job-page` 和 `/social/job-page` 工作正常 — 详情页可能用另一个内部接口，需要更多 headers / cookie。

**结论：** 不是我们 URL pattern 错，是上游 lixiang.com 自己的详情页和我们用的列表接口数据不联通。需要：

a) 上游修复（看 lixiang 是否会上线公网详情页 — 看 employ/campus.html 截图，他们的求职流程是搜索 → 直接申请，可能根本不打算开放 detail deep-link）
b) 反向研究详情页用的另一个接口的请求形式

二者都超出 URL 体检范围。本轮不修。

## URL 体检 — 收尾

8 家公司的 detail URL bug 全部修完。剩下 50 - 8 = 42 个 adapter 经过两轮体检（curl + browser）均为 PASS（或不可测的 hash-only SPA 但和官网 list 链接一致）。
